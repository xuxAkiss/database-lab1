# 完整填写流程：实现说明

本轮在既有认证、问卷版本与 MongoDB 上新增填写功能，不实现统计页面。固定 `/s/{share_token}` 现在提供实际填写；原 `/api/shared/{token}` 结构读取接口保持兼容。

## 页面操作

登录后进入分享链接，点击“开始本版填写”。输入约700毫秒后自动保存，也可点“立即保存”。页面分别显示待保存、保存中、已保存、失败；刷新可恢复服务器草稿。输入未完整也能存草稿；下一题校验当前题，提交校验全卷。数字输入用文本控件，以保存 `-`、`1e` 等未输入完成的形式。

有跳转规则时，导航仅允许已访问题目；结束页另提供缺失/不合法必答题的补答入口。无任何自动跳转规则时可自由导航。返回修改保存后由服务器撤销旧链并重新计算队列。页面显示已访数量、待答顺序，不能直接修改服务器状态。

“前往提交检查”仅在无跳转的自由问卷、所有题已访或存在有效结束来源时可用（越权请求由服务器拒绝）。结束页列出全卷错误；“确认提交答卷”成功后显示历史记录 ID 与该账号该版本的提交序号。允许重复时，需明确点“开始下一次空白填写”。

并发冲突或保存结果不明时暂停自动重试，保留当前控件和可复制的未保存内容。用户明确重新读取后才替换本地界面；不自动覆盖服务器更新。修改时有未保存离页提醒；浏览器关闭瞬间不保证网络保存完成，应以“已保存”为准。

旧版草稿可从页面入口查看，只读、不搬入新版。关闭/到期时也允许登录者读取自己的草稿，但本轮默认暂停新建、修改和提交；同版重开/延长截止后恢复原草稿。

## 本轮采用的明确默认值

- 文本按 Unicode 码点计数，排除 Unicode White_Space 字符：U+0009–000D、0020、0085、00A0、1680、2000–200A、2028、2029、202F、205F、3000；不把零宽空格、BOM 自动当成空白。不改变原始文本。
- 非必答空答案（文本全为上述空白也视为空）不执行最小长度、最少/恰好数量、数字下界。非空答案仍执行所有限制。必答空值总是拒绝。
- 单选存选项ID字符串；多选存去重校验后的合法ID列表，按选项原序规范化；文本存原文；数字保存十进制/科学计数法原文，最终按现有有限 IEEE-754 数值规则验证。数字不接受布尔、NaN、Infinity或任意对象；部分数字仅可作为草稿，不能通过下一题/提交。
- 草稿允许超出业务上下限的中间内容，以便继续修改。存储形状仍严格校验：题目须是当前题、选项须存在且不能重复；数字原文最多128字符、文本草稿最多20000码点。最终长度以版本配置为准。
- 自动保存有效完整答案时即重算该题来源与待答安排，但不自动离开当前题；“下一题”才执行导航。部分非法答案撤销旧来源，但不产生新来源。
- 手动返回已访题目后，改变答案所产生的新来源视为这次明确改答的独立来源。仅返回未改答不会让已有来源自动变成独立来源。原已访集合与答案不因撤销而删除。
- 开始下一轮替换该账号/版本已消费的当前草稿槽位；旧答案已独立存在 submissions 中。不会无限累积同版已消费草稿副本；不同版本的草稿槽位保留。

## 当前状态与来源图

`state` 保存 `answers`、`current`、`visited`（去重访问顺序）、`pending`、`ended`、`sources`、`contexts`、单调 clock。

每个有效来源节点保存：内部 id、question_id、parents（支持它的上游来源）、root（独立来源）、targets、end、rank。每题最多一个当前有效来源。进入一个未访目标题时记录当时支持它的全部来源；普通顺序/明确手动进入的题为根上下文。

改答先删除该题旧节点，再递归删除“全部父来源都已失效”的后代。还有其他父来源的节点保留，并去掉失效父边。答案和已访题保留。之后若新答案完整有效，按其匹配规则创建新节点。它的目标按题序升序，按最新激活来源优先组合，最后追加原顺序全部未访题，全局去重。保留来源节点直到失效，即使目标已执行，也能解释连锁撤销；已访目标永不自动再入队。

例如 1→[3,5]、3→7，顺序为 1,3,7,5,2,4,6。不同来源可以共同支持同一目标；队列只显示一次，图保留多来源。来源图是当前有效因果状态，不是按键事件历史或通用事件平台。`pending` 虽可从图重算，仍随同一份原子草稿保存，方便恢复与检查；每次变更由服务端重算保证一致。客户端没有设置 visited/pending/sources 的接口。

结束跳转只停止普通导航，不免除必答与已填写内容的校验。补答可进入未访必答题，返回检查时再次全卷校验；不会自动填答案。补答产生的新规则仍按同样的状态机计算。

## MongoDB 数据和索引

| 集合 | 职责 | 主要唯一约束 |
|---|---|---|
| fill_drafts | survey_id、version_id、user_id、attempt_id、previous_attempt_id、revision、status(active/submitted)、state、updated_at | survey_id + version_id + user_id |
| participations | 同账号同版本 submission_count、latest_submission_id | survey_id + version_id + user_id |
| submissions | 每次独立成功历史；版本、账号、attempt_id、draft_revision、request_key/hash、sequence、answers、submitted_at | version_id + user_id + sequence；version_id + user_id + request_key |

所有账号身份从服务端会话取得。匿名仍关联 user_id，用于资格、序号、幂等和未来按账号取最新；填写接口仅返回本人的草稿和提交结果，不返回 user_id。没有创建者读取参与者/草稿/答卷列表接口，既有管理接口也未增加这些数据。

每个草稿 attempt_id 标识一次填写，revision 标识每次状态更新。旧 attempt 或旧 revision 的保存不可能更新新轮次。已提交草稿标为 submitted，只有授权的明确下一轮操作可换新 attempt；保存接口不使用 upsert，不能复活已消费草稿。

## 事务、并发与提交重试

开始、状态操作、提交均复用既有事务封装（snapshot/majority，总预算10秒）。每个写入事务首先对 **surveys 同一文档真实 `$inc fill_fence`**，发布和关闭也写此文档，建立共同协调点；不是只读一下状态。并发旧快照写入会冲突并重试，然后重新检查版本、关闭和截止。该做法会串行同一问卷的写入，适合本课程规模，未声称适合高并发生产负载。fill_fence 不改变创建者的 state_revision。

截止判定点：取得问卷写协调后，本应用服务器 UTC 的最终检查时间 `checked_at`；此时已截止拒绝。若检查时未截止而事务提交完成稍晚，仍按该判定点接受。submitted_at 统一截为 MongoDB 毫秒精度，使首次和重试结果一致。未做系统时钟同步保证。

提交事务原子完成：写入新历史 → participation 序号加一、最新引用切换 → 草稿消费。禁止重复在相同账号/版本内检查成功次数。未成功的新草稿不改变旧最新引用。

请求键作用域为账号＋版本。请求内容由 attempt_id＋revision 标识和哈希绑定；答案只能在新 revision 修改，因此无需在提交请求再上传一份不可信答案。同键同内容返回原结果，同键不同修订/轮次409。查询已成功结果发生在版本/开放检查之前，因此旧版成功提交在切换后仍可原样重试；未成功的旧版请求拒绝，绝不转记新版。

浏览器 sessionStorage 仅保存未确认提交的请求键、版本、attempt、revision（不存答案、身份凭据），便于刷新后点“重试上次未确认的提交”；业务事实仍全部在 MongoDB。服务端操作超时可能结果未知，请用原键重试，不随意换键。

## API

全部需登录，POST 复用原 require_mutating_user（Origin、Cookie、CSRF）。额外字段拒绝；不接受客户端 user_id、来源图或已校验标记。

| 方法 / 路径 | 内容 |
|---|---|
| GET /api/fill/{token} | 当前版本结构、自己的当前草稿、自己的旧版草稿摘要、自己的提交次数与最新引用；关闭也可只读 |
| GET /api/fill/{token}/drafts/{version_id} | 仅此账号此版本草稿和对应不可变结构；无自己的草稿则404 |
| POST /api/fill/{token}/start | `{version_id, new_attempt?:false, previous_attempt_id?:...}`；首次/恢复或明确开始下一轮 |
| POST /api/fill/{token}/drafts/{version_id}/action | `{attempt_id, revision, action}`；save 还需 question_id/value；goto 需 target；next/finish 不夹带答案 |
| POST /api/fill/{token}/drafts/{version_id}/submit | `{attempt_id, revision, request_key}`；返回 submission_id/version_id/sequence/submitted_at |

状态冲突/版本切换/关闭/截止/消费409，答案校验422并给 question_id，未登录401，CSRF403，无所属草稿404，数据库错误沿用脱敏503。服务端最终校验，不以按钮隐藏作为权限控制。

## 真实问题与修复者

- AI 编写后第一次真实集成发现：首次提交结果的 datetime 为微秒精度，MongoDB 重读为毫秒，造成幂等响应时间字符串不一致。AI 将 submitted_at 规范为毫秒，真实复测同键结果一致。
- 第二次测试的某断言将直接服务调用的 Python datetime 与 HTTP JSON 日期字符串直接比较，产生测试失败。AI 修正测试为解析后的时间与其余字段比较；没有将此错误描述成数据库或业务失败。
- 浏览器发现：自动保存后队列和修订标签未立即刷新，以及开始下一轮仍残留“此轮已提交”状态文案。AI 分离元数据刷新以保留输入焦点，同时更新新轮次状态文案；保存后的队列/修订显示已在浏览器复查。
- 环境准备与加强版并发测试各发生一次自动权限审核超时，相关命令当次未执行；均按工具允许重试一次后成功。没有绕过目录限制或把超时解释成测试通过。
