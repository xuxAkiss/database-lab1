## 二、原设计与本次调整

### 2.1 第一阶段的设计

系统后端采用 Python、FastAPI 和 PyMongo，前端使用普通 HTML、CSS 和 JavaScript，由同一个后端提供页面。所有业务数据存储在 MongoDB 中，没有使用关系数据库或现成问卷系统框架。

第一阶段将题目、选项、校验条件和跳转规则嵌入问卷结构。编辑稿可以修改，发布时生成不可变的问卷版本。填写草稿和成功提交分别保存，每次成功提交都追加一份历史答卷。统计时，在一个确定的问卷发布版本内，按账号选取最新成功的整份答卷。

这种设计能完整保留每次发布时的问卷内容，但题目只有本卷内的身份。将“你的年龄”复制到另一份问卷后，系统无法仅凭文字确认两道题是否同源，也无法可靠地记录独立题目的修改历史。

### 2.2 新需求带来的问题

题目复用需要稳定的身份，否则跨问卷查询只能依赖不可靠的标题比较。共享又带来了两个边界：修改题库中的内容不能改变已经发布的问卷；撤销共享也不能抹掉别人此前合法保存的问卷快照。

跳转规则同样不能直接照搬。例如，原卷的一道题跳到第 5 题，换到另一份问卷后，第 5 题可能已经是完全不同的问题。因此，题目定义可以复用，但跳转关系必须留在具体问卷中。

### 2.3 修改范围

| 原有部分 | 第二阶段的调整 | 保留的行为 |
| --- | --- | --- |

| 填写与提交 | 继续使用原状态机和提交接口 | 草稿恢复、跳转、校验、历史追加与事务一致性 |

## 三、MongoDB 数据设计

### 3.1 原集合与新增集合

| 集合 | 保存的内容 | 第二阶段处理 |
| --- | --- | --- |
| `users`、`sessions` | 账号、密码散列与服务端会话 | 沿用 |
| `surveys` | 问卷归属、固定链接、当前版本及开放状态 | 沿用 |
| `survey_edits` | 可修改的问卷结构与修订号 | 题目实例可增加 `source` |
| `survey_versions` | 不可变的发布快照 | 新发布可包含题目来源，旧版本不回写 |
| `fill_drafts` | 当前答案、填写位置、待答顺序与来源关系 | 沿用 |
| `participations` | 账号在指定发布版本中的参与状态 | 沿用 |
| `submissions` | 每次成功提交的历史答卷 | 保留历史，增加跨问卷统计索引 |
| `questions` | 独立题目的身份、作者、共享账号和版本序号 | 新增 |
| `question_versions` | 题目定义、父版本、恢复来源及派生来源 | 新增 |
| `question_banks` | 个人题库名称、成员题目和修订号 | 新增 |

题目保留三种标识：本卷实例 ID 用于填写和跳转；独立题目 ID 标识题资源；题目版本 ID 固定本次使用的内容。调整题库版本不会替换问卷中已保存的内容。

下面是来源字段的示意，实际值由服务端生成和校验：

```json
{
  "id": "本卷题目实例ID",
  "source": {
    "question_id": "独立题目ID",
    "version_id": "固定的题目版本ID"
  }
}
```

题目实例仍保留题型、题干、选项、校验条件和本卷跳转规则，不会在每次填写时重新读取题库中的最新内容。旧题没有 `source` 也能继续发布、填写和进行单卷统计。

### 3.2 嵌入、引用与冗余的取舍

不同题型需要的字段不同，使用文档保存完整题目定义比较自然。问卷发布快照则将填写需要的结构嵌入保存，读取一个版本就能获得当时的题目、选项和规则。

独立题目的版本采用单独集合，避免把不断增长的修改历史放进一个文档。题库只引用题目身份，选题时再固定具体版本。问卷同时保留来源和内容快照，会产生一定冗余，但这保证了历史含义稳定，也使已保存问卷不依赖题库当前的共享权限。

这里继续采用嵌入与引用结合的方式：整卷读取的内容保留在快照中，跨卷复用的资源通过 ID 关联。关系数据库也能实现这些功能，但 MongoDB 是课程要求，文档模型也适合保存不同题型和完整版本结构。代价是内容快照重复，以及新增版本、共享和引用时需要跨集合协调。

### 3.3 约束、索引与事务

`question_versions` 对 `(question_id, number)` 建立唯一索引，保证同一题目下版本序号唯一。题目作者、共享账号、题库所有者及问卷中的题目来源设置相应查询索引。跨问卷统计新增以下索引，用于定位某卷某版内各账号的最新提交：

```text
submissions(survey_id, version_id, user_id, sequence 降序)
```

MongoDB validator 负责基本字段类型和文档形状，应用层负责跨字段校验、引用合法性、归属和版本不可变规则。新增 schema 安装脚本可重复执行，预检失败时停止，不删除已有数据。

创建题目及初版、创建后续版本、旧题导出关联等跨文档操作使用事务。版本号由服务端原子分配，事务冲突重试与唯一索引共同防止并发覆盖。共享撤销和新引用保存通过共同的授权协调字段确定先后，避免在权限已经失效后仍保存新的引用。

## 四、题目版本、共享与填写逻辑

### 4.1 版本分支与恢复

题目版本保存后不提供原地修改接口。修改会生成新版本，并记录它从哪个版本发展而来。例如，可以从 V1 分别生成 V2 和 V3，让两份问卷采用不同分支。

恢复旧版也会追加一个版本。若当前在 V3，希望恢复 V1 的内容，系统生成 V4，同时记录本次操作的父版本和恢复来源。V2、V3 仍然保留，已有问卷不会自动换版。问卷编辑稿显式换题版本后，还需要重新发布才影响线上内容。

共享接收者可以读取和使用题目，但不能修改原作者的题目。需要调整时，可以派生一个自己拥有的新题目并保留来源。派生题具有独立身份，不能因为题干相同就与原题合并统计。

### 4.2 共享与使用查询

共享面向指定的已注册账号。撤销后，接收者不能再从原题库读取或新增引用，但自己已经合法保存的问卷快照仍然可用。题目共享不会授予查看他人答卷或统计结果的权限。

使用情况查询区分编辑稿、当前发布和历史发布。对自己的问卷展示具体引用；对他人的问卷只展示匿名引用次数，不返回私有标题、链接、账号或答卷。这些次数表示引用次数，不等于去重后的问卷数或填写人数。

### 4.3 跳转与校验

独立题目定义不保存本卷跳转目标。导入题目时创建本卷实例并清空跳转规则；对已有实例换版时保留本卷规则，再检查选项、目标、循环和条件是否仍然有效。新版删除了旧规则引用的选项时，系统拒绝非法结构并提示处理，不静默删除规则。

填写继续使用第一阶段规则：跳转改变优先回答顺序，不永久跳过中间题。例如 1 跳 5，后续顺序为 `1→5→2→3→4→6`；连续跳转优先处理新的目标。多选跳转按完整选项集合匹配，目标去重；返回改答会撤销旧路径的未执行贡献，但保留已经回答的内容以及其他有效来源。跳到结束仍需检查全卷必答题。

校验继续由后端最终执行，包括单选合法选项、多选数量、文本长度、数字范围和整数条件。草稿使用修订号避免迟到保存覆盖新内容；成功提交追加保存，不能用新答卷覆盖旧历史。

## 五、跨问卷统计设计

### 5.1 统计范围

一次查询固定一道题的一个版本，只汇总当前用户拥有的问卷。同名题、派生题和恢复产生的新版本不会自动合并。默认使用各卷当前发布版本，也可以为某卷明确选择一个历史发布版本，替换它的当前版。

每个纳入的问卷版本先按账号选最新成功的整份提交，再读取目标题答案。因此，最新答卷留空时不会回填旧答案，未提交草稿也不进入统计。同一个账号填写两份问卷会贡献两份回答，页面称为“回答数”，不称为独立人数。

同一题目版本在一卷中出现多个实例时，默认选择顺序中的第一个，并显示可选实例供用户切换，避免不知情地重复计数。这个默认规则属于实现选择，不是教师原文指定的规则。

### 5.2 先选最新整份答卷，再跨卷汇总

查询在一次 MongoDB 快照事务中读取问卷归属、发布指针、版本结构和最新答卷，避免查询期间切版导致结构与答案来自不同时间点。主要步骤是：

1. 确定自己拥有的问卷及本次选择的发布版本。
2. 按题目 ID 和题目版本 ID 匹配实例，检查显式选择是否有效。
3. 按问卷和发布版本筛选提交，再按账号和提交序号选最新整份答卷。
4. 读取选定实例的答案，分别统计有效、空白和无效回答。
5. 返回实际纳入的问卷、发布版本、题实例及统计结果。

单选、多选展示选项计数，比例分母为有效回答数，多选比例之和可能超过 100%。文本展示回答内容；数字展示平均值和数值频数。数字 0 是有效值，空白不按 0 处理。详情分页不会把当前页误当作全量结果。

统计响应不包含填写账号、会话和答卷关联标识。文本答案本身可能包含填写者主动输入的姓名等信息，因此这里不声称文本内容已经自动脱敏。

### 5.3 主要接口

| 接口 | 用途 |
| --- | --- |
| `GET /api/questions`、`POST /api/questions` | 查询、创建独立题目 |
| `GET /api/questions/{id}/versions` | 查看版本历史 |
| `POST /api/questions/{id}/versions` | 基于父版本修改或恢复旧内容 |
| `POST /api/questions/{id}/share` | 授予或撤销指定账号的使用权限 |
| `GET /api/questions/{id}/usage` | 查询题目引用情况 |
| `/api/question-banks` 及成员、改名接口 | 管理个人题库 |
| `POST /api/surveys/{id}/questions/{instance}/export` | 将自己编辑稿中的旧题保存到题库并关联来源 |
| `GET /api/question-statistics/{id}/scope` | 获取当前用户可查询的题版本与问卷范围 |
| `POST /api/question-statistics/{id}/query` | 按明确范围计算跨问卷统计 |

统计查询虽然使用 POST 提交结构化筛选条件，但不写业务数据，仍沿用现有会话、Origin 和 CSRF 校验。未登录、无权限、非法选择、范围超限等情况返回明确错误，不伪装成零结果。完整请求字段和状态码见仓库中的 API 文档。

### 6.3 旧数据与兼容处理

对第一阶段基线的 525 条业务记录，以及包含题库成果的 762 条本轮前基线记录，分别逐条读取并比较 SHA-256，结果均一致。这两组记录存在包含关系，不能相加；自然变化的会话记录未纳入该基线。

旧题没有可靠来源时，不按标题猜测，也不改写历史发布和答卷。用户可以将编辑稿中的旧题显式保存为独立题目，系统原子记录来源并关联当前编辑稿，但不会反过来声称更早的历史题目已经得到同源证明。

当前代码能够兼容旧数据，并不意味着可以直接降级为第一阶段代码。旧模型不接受新增的来源字段，回退需要先停写、备份，在副本验证兼容处理，并保留第二阶段的新历史。项目没有进行完整灾难恢复演练。

## 七、AI 使用总结与个人贡献

### 7.1 AI 帮了什么

第二阶段分两轮推进：先完成题库、版本、共享和问卷复用，再完成跨问卷统计与整体验收。每轮提供原作业、需求变更和已有代码，要求保留旧数据，完成实现后测试、修复并回归。

AI 帮助阅读现有代码，编写接口、页面、schema 和测试，执行数据库与浏览器验证，并整理文档。使用的工具包括 Codex、PowerShell、Python/PyMongo、MongoDB、Playwright 和 Microsoft Edge。完整提示词与结果保存在项目开发日志中。

### 7.2 AI 做错了什么

跨问卷页面最初沿用旧页面样式，交互测试虽然通过，但截图中固定提示条遮挡了范围说明，频数表的列间距也过窄。AI 检查截图后增加了该页面专用样式，取消固定提示、调整表格和移动分页布局，再重跑完整浏览器流程。这说明接口和交互断言通过后，仍需要检查页面实际呈现。

### 7.3 自己改了什么

我修改的是需求解释和实施方案。第一阶段撤销了“重复提交覆盖旧答卷”，改为保留每次成功提交；第二阶段要求继续沿用这一规则，并明确保留原核心结构、旧数据和演进证据。我提出修改意见，再由 AI 落实到代码和测试中。

程序编写、修复和测试执行由 AI 完成，我主要负责需求判断与结果审阅。

### 7.4 自己设计了什么

我选择并确认了版本和统计规则：题目各版本分开统计，同账号跨卷分别贡献回答，每卷内取最新整份成功提交；历史发布版本替换该卷当前版本，不自动混合；共享题目不授予答卷权限，跨卷只统计自己的问卷。原有的重新发布切版、旧草稿保留但不可提交到新版等规则继续沿用。

部分方案由 AI 提出，我在解释后确认。集合字段、索引、事务和具体实现主要由 AI 设计并落实，我的贡献主要是业务规则和方案取舍。

### 7.5 遇到的问题与解决方式

| 问题 | 处理方式 |
| --- | --- |
| 本地数据库未运行，连接被拒绝 | 使用已有启动脚本和原数据目录启动，没有重建数据库 |
| 浏览器测试依赖下载超时 | 在项目虚拟环境内重试安装，未修改基础 Python 环境 |
| 页面交互通过但视觉呈现有问题 | 检查截图，修复专用样式，再执行相同流程复测 |
| 换题版本可能使旧跳转条件失效 | 保留本卷规则后全量校验，拒绝失效引用并提示处理 |
| 旧题缺少可靠来源 | 保持原功能可用，不推测同源；提供显式保存和关联入口 |

## 八、提交材料与复现

powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\dev\mongodb\Start.ps1

## 九、已知限制
